# 健康减脂与血糖管理 PWA
## V1.0 产品需求与 Codex 开发任务书

**项目代号：** HealthTrack  
**版本：** PRD V1.0  
**状态：** 待开发  
**开发方式：** Codex + React + TypeScript + Supabase + Netlify  
**目标平台：** 手机 PWA，优先适配 Android / 小米手机

---

# 1. 项目目标

开发一套个人专属的健康管理系统，用于长期管理：

- 体重、体脂、腰围
- 饮食、热量及营养结构
- CGM 动态血糖及指尖血糖
- 血压
- 运动、步数、饮水和睡眠
- 疾病、用药及医疗档案
- 医院检验报告
- AI 健康分析与减脂建议

核心原则：

1. 所有健康数据统一存储在云端数据库。
2. 手机端是日常记录和查询入口。
3. ChatGPT 是后续的智能分析与数据交互入口。
4. 历史记录永久保留，新增记录持续积累。
5. 不依赖聊天记录作为唯一数据存储。
6. 个人健康数据不对外公开，不加入广告和会员体系。

## 迁移规则（强制要求）

**开发期间：**
- 现有 Excel 继续作为主要健康数据档案。
- 用户每天新增的数据继续按现有流程保存到该档案。
- 不要求用户暂停日常记录。
- 不允许 Codex 擅自修改、覆盖或删除原始 Excel。

**迁移阶段：**
- 首次导入全部历史数据。
- 记录首次导入的时间和批次。
- 对开发期间新增或修改的数据进行增量补录。
- 根据唯一标识和记录内容防止重复导入。
- 比对源文件与数据库的数据数量、日期、数值、单位和来源。

**正式上线：**
- 验证迁移结果。
- 验证备份与恢复。
- 正式切换为云端数据库作为唯一主数据源。
- Excel 保留为可下载的备份副本。

注意：ChatGPT Library 中的 Excel 不会自动出现在 Codex 本地项目目录中。需要用户提供本地副本进行迁移。该文件必须放在 Git 忽略目录中，不能提交到公开或私人代码仓库。

# 3. 产品界面

采用移动端优先设计。

底部固定四个导航入口：

## 3.1 今日首页

展示：
- 最新体重
- 今日饮食热量
- 蛋白质、碳水、脂肪
- 今日血糖状态
- 今日血压（如有记录）
- 今日运动量
- 睡眠时间
- 今日记录完成情况
- AI 每日健康总结

没有记录的数据必须显示为空或“未记录”，不能自动填零。

## 3.2 快速记录

支持：
- 体重记录
- 腰围、体脂记录
- 饮食拍照
- 手动饮食记录
- 血糖记录
- CGM 数据导入
- 血压记录
- 运动和步数
- 饮水量
- 睡眠
- 用药记录

常用记录尽量在 3 步内完成。

## 3.3 趋势分析

支持 7 天、30 天、90 天及自定义日期范围。

展示：
- 体重趋势
- 体脂趋势
- 每日热量
- 三大营养素结构
- CGM 血糖曲线（仅在具备原始数据时）
- TIR、TBR、TAR、平均血糖、CV
- 血压趋势
- 运动及睡眠趋势

支持不同日期区间对比。

## 3.4 健康档案

分类管理：
- 个人基本资料
- 疾病和健康问题
- 当前用药
- 用药历史
- 医院检验报告
- CGM 报告
- 复查计划
- 重要健康事件
- 文件及图片附件
- 数据备份和导出

# 4. 饮食 AI 功能

这是第一版的重要特色。

工作流程：

1. 手机拍摄餐食。
2. 上传图片至受保护的服务端接口。
3. OpenAI API 识别食物。
4. 估算食物名称、份量和重量。
5. 估算热量、蛋白质、碳水、脂肪。
6. 用户核对并修改。
7. 用户确认后保存数据库。
8. 自动汇总当日饮食。

要求：

- 支持一餐多种食物。
- 支持拆分食物项目。
- 支持修改份量。
- 支持删除识别错误项目。
- 支持手动录入。
- 明确区分 AI 估算与实际称重。
- 记录估算来源和不确定性。
- 不得把 AI 估算值伪装成实验室或设备实测值。

AI 不可用时，手动记录功能必须正常。

# 5. 血糖管理

支持三类数据：

1. CGM 连续血糖数据。
2. 指尖血糖数据。
3. CGM 周期报告统计数据。

血糖记录字段：

- 测量时间
- 血糖数值
- 单位
- 测量方式
- 餐前/餐后
- 距离进食时间
- 相关症状
- 指尖复核结果
- 处理情况
- 数据来源

CGM 周期报告支持：

- 平均葡萄糖
- eHbA1c
- TIR
- TBR
- TAR
- CV
- 观察开始日期
- 观察结束日期
- 设备及报告来源

必须区分不同观察周期的数据。

没有原始 CGM 数据时，不得生成虚假的连续曲线。

系统可以提示可能的异常和复核需求，但不自行诊断、不自动调整药物剂量。

# 6. 数据库设计

推荐 Supabase PostgreSQL。

主要数据表：

| 表名 | 作用 |
|---|---|
| profiles | 个人基础信息 |
| body_measurements | 体重、体脂、腰围 |
| meals | 餐次及饮食记录 |
| meal_items | 食物和营养明细 |
| glucose_records | 单次血糖 |
| cgm_reports | CGM 周期报告 |
| cgm_readings | CGM 原始读数（未来扩展） |
| blood_pressure | 血压 |
| daily_lifestyle | 运动、步数、饮水、睡眠 |
| medications | 药物档案 |
| medication_logs | 实际用药记录 |
| lab_results | 医院化验结果 |
| health_events | 重要健康事件 |
| attachments | 报告和图片附件 |
| audit_logs | 数据变更审计 |
| import_batches | 历史数据导入批次 |

## 通用字段

业务记录原则上包括：

- id
- user_id
- recorded_at
- created_at
- updated_at
- source_type
- source_reference
- notes

其中 source_type 至少支持：

- user_input
- device
- lab_report
- ai_estimate
- excel_import

需要保留原始数据及其来源。

## 数据完整性规则

1. 未记录的数据使用 NULL，不使用 0。
2. 保留原始单位。
3. 数据修改需要可追溯。
4. 导入需要幂等处理，避免重复。
5. 原始报告数据与 AI 分析结果分开保存。
6. 每个用户只能读取和修改自己的数据。
7. 所有记录采用明确的时间和时区规则。

每日汇总数据优先通过查询或视图计算，避免重复维护两套相互矛盾的统计值。

# 8. 隐私和安全要求

这是个人医疗健康数据系统，安全要求为 P0。

必须实现：

1. 登录认证。
2. 数据库 RLS 行级访问控制。
3. 私有文件存储。
4. 安全的文件访问授权。
5. API 密钥仅存储在服务端环境变量。
6. 不得将 OpenAI Secret Key 或 Supabase Service Role Key 放入前端。
7. 不得将真实健康数据提交至 Git。
8. 不得在日志中输出敏感医疗信息。
9. 支持数据导出。
10. 支持完整备份与恢复验证。
11. 数据修改应可追溯。
12. 用户能够删除自己的数据。

Service Worker 不得缓存敏感医疗数据和完整医疗报告。

离线模式仅提供有限的记录草稿能力，并且必须处理重复提交和同步冲突。

# 9. AI 功能的开发策略

第一版先实现基础记录，不让 AI 成为系统运行的必要条件。

AI 功能分为：

P1：
- 食物图片识别
- 热量和营养估算
- 每日饮食总结
- 每周趋势分析

P2：
- ChatGPT 双向数据交互
- 更丰富的个性化分析
- CGM 数据自动同步

要求：

- 设置每月 API 预算。
- 支持调用次数限制。
- 支持异常重试。
- 防止重复调用。
- 显示 AI 估算与实测的区别。
- 用户确认后才能将 AI 结果写入正式记录。

ChatGPT 双向同步必须使用单独的、经过身份验证的 API 接口，不得直接向浏览器暴露数据库管理密钥。

# 11. 验收标准

第一版正式发布必须满足：

- 手机桌面可以正常打开 PWA。
- 所有核心记录支持新增、修改和查询。
- 真实健康数据可以正确展示。
- 历史 Excel 数据完整迁移。
- 开发期间新增的数据没有遗漏。
- 不存在重复导入。
- 不同账号之间的数据隔离有效。
- API 密钥没有暴露。
- AI 识别错误可以人工修改。
- 数据可以完整导出。
- 数据备份能够实际恢复。
- 断网草稿不会无提示丢失。
- 重新联网不会重复写入记录。

没有完成上述验收，不得将项目标记为正式上线。

# 12. Codex 工作约定

以下要求对整个开发过程生效：

1. 每次只完成一个明确阶段或功能。
2. 修改前先检查相关文件。
3. 不随意重构已经正常工作的功能。
4. 不删除原始数据和文件。
5. 不在未经确认时执行生产数据库操作。
6. 不擅自创建可能产生费用的云服务。
7. 不提交 API Key、密码或真实健康数据。
8. 修改数据库 Schema 必须保留迁移脚本。
9. 每个功能完成后运行相应测试。
10. 测试失败时先查明原因，不允许跳过测试来宣布完成。
11. 每个阶段提交清晰的变更说明。
12. 遇到架构选择、收费、权限和数据迁移等重要问题，先向用户说明并等待确认。

优先使用 Git 分支开发，阶段验收后再合并。
